# MUCPlayground

**Write MUCOM88 MML in the browser and hear it right away.** Written by ToughkidCST.
Open it at **https://toughkiddev.github.io/MUCOMSX/MUCPlayground/**

- **한국어:** 브라우저에서 MUC(MML)를 입력하고 바로 들어볼 수 있는 연습 공간입니다. 설치할 것이 없습니다.
- **日本語:** ブラウザでMUC（MML）を書いて、すぐに試聴できる練習用スペースです。インストールは不要です。

## What it does

- Type MML in the editor and press **Play** (`Ctrl+Enter`). `Esc` stops.
- **Text size:** the *Text* slider at the top, left of the language switch, sets the editor's font size (10–24 px); line numbers, colouring, error marks and playback highlights follow, and the size is remembered.
- **Menus size:** the *Menus* slider next to it enlarges the header, toolbar buttons, side panel (messages, files, quick reference), the editor's bottom bar, the footer and the samples dialog from 100 to 200 %, for anyone who finds the interface hard to read. It applies when the slider is let go, is remembered, and is limited on narrow windows so the panels still fit (100 % per 640 px of width: a phone stays at 100 %, 1280 px and wider allow 200 %).
- **MML colouring:** parts (in their playback colour), notes, commands, numbers, loops and brackets, macros, tags and comments each have their own colour.
- **Suggestions while typing**, like a code editor: type a command letter, `@`, `*`, or `#` / a part letter at the start of a line and a list appears with each command's argument form and a one-line explanation (English, Korean or Japanese). Only commands that apply to the part's type (FM, SSG, rhythm, ADPCM) are offered; `@` also lists the voices defined in the song (on an SCC part, its `@W` / `?WD` waves) and `*` its macros. `?` on an MSX or SCC part lists the MucoMSX chip extension commands for that chip (PSG, SCC, MSX-MUSIC or the `MSXG` drums), and `?` at the start of a line the global resources (`?WD` wave, `?IU` OPLL voice, `?IT` drum kit, `?KT` pitch table, `?IM` program map, `?WS` bank wave), filled in with a working example. `Ctrl+Space` opens the list anywhere; `Tab` or `Enter` inserts, `Esc` closes. Typing notes never opens it. Command descriptions come from the MUCEdit manual (`mml-reference.js`).
- **Checked as you type:** shortly after you stop typing the song is compiled in the background, without interrupting playback, and errors and warnings are underlined and marked in the margin.
- **Detailed compiler messages.** Each error or warning shows its code (E0498, W0408 …), line, column and part, the source line with a `^` under the spot, the compiler's own words, and an explanation of **what it means**, **how to fix it** and, for a command, its **correct form**, in English, Korean or Japanese. When the compiler fails without saying where (a crash on `l0`, an unexpected character), the playground finds the line itself by recompiling shortened copies of the song. Click a message to jump to it: its line is marked with a red (error) or yellow (warning) line until you edit the text or open another song (opening a song also clears the old messages until the new one is checked). Voice warnings such as W0408 name only the voice number; the playground points them at the line that defines or first uses that voice.
- **While a song plays, the command each part is playing is highlighted in the editor**, one colour per part, in step with what you hear. The editor follows the playing part (pick which one under *Now playing*, or turn *Follow playback* off). This includes MUCOMSX songs: their `MSXA`–`MSXK` and `SCCA`–`SCCE` parts are shown under those names (see `src/Engine/MsxTrace.cs`).
- **Tracker mode (experimental):** **🎼 Tracker** under the editor splits it: the MUC text on the left, the song as a tracker pattern on the right, in Furnace's dark style. Every part is a column; each row is a fixed number of clocks (*Row*: 1/4 to 1/64 of a whole note); a cell shows the note starting there (`C#4`), its voice (`@`) and volume (`v`) in hex, `OFF` where a rest follows a note, and a bar while a note is held; rows are numbered in hex within 64-row patterns. Notes that come from a repeat or a macro are dimmed (they are written once in the text). Both sides stay in step: moving the caret in the text moves the tracker's cursor to that note, and clicking a cell marks its token in the text; editing the text redraws the tracker, and the tracker is edited directly: click a cell and type it the way the tracker shows it: a note as `C#4` / `D-5` / `C4` (letter, `#` or `-`, octave 1–8), `OFF` for a note off, `...` for a rest, two hex digits in the `@` and `v` fields. A box over the field shows what is typed, in that format, and closes by itself once the value is complete; `Enter` takes an unfinished one (`C` at the octave shown above, `3` as `03`) or opens the field with what it shows, `Esc` cancels. Chosen under *Input*, Furnace's quick keys (`Z S X D C …` / `Q 2 W 3 E …`) enter a note with one key instead. The note is heard on the keys' synthesizer. `Delete` (or **Rest**) turns a note into a rest, `1` (or **OFF**) puts a note off, and with the keys mode piano open (**🎹**) its keys write into the tracker too, so it can be edited by touch. An edit rewrites the token behind the cell: a new pitch (with `>` / `<` around it when it is in another octave), or the note or rest cut in two when the cell lies inside it (`c4` → `c16 e8.`). Below a part's last note (the tracker shows one more pattern) the note is added to the part's text, the note before it held up to there (`d4` → `d2 c16`); a part with no notes yet has a column too. The `@` and `v` values set the voice and volume of the note starting there (an `@n` / `vn` before it is changed, or one is written). Octave marks that cancel out (`><`) are not left in the text. A line written by several parts (`BC …`) is changed for all of them, which the tracker points out; it is never lengthened when adding notes. Arrows, `PgUp` / `PgDn` move; numpad `/` `*` change the octave. While a song plays, the pattern scrolls with it, the playing row in the middle (from the engine's trace, so MUCOMSX songs too); scrolling by hand pauses that for a moment. The timeline is read by `mml-timeline.js` the way MUCOM88's compiler counts clocks (lengths, dots, `%`, `^`, `&`, `[ / ]`, macros, `s`, `\` echoes, `C`): it matches the driver note for note on all the templates; tied, portamento and echo notes are shown but edited in the text.
- **Voice bank:** **🎛 FM bank** and **〰 SCC bank** in the *Voice / PCM files* panel, next to *Add voice / PCM*, split the editor like the tracker (each opens the bank on its tab; the tabs at the top switch too): the text on the left, the song's FM voices as a list on the right. The list joins the voice file the song uses (`#voice`, or `voice.dat`, which the compiler looks for when there is no tag) and the voices the MUC defines itself (`  @n` and `  @%n` forms), each marked `DAT`, `MUC`, or `MUC▸DAT` where the MUC defines a number the file has too (the MUC's wins, as in the compiler), with its name, algorithm, feedback and how many notes of the song use it. Click a voice to hear it, double-click to write `@n` at the caret. **Add** puts Furnace's default voice at the first free number, **Del** removes it (asking when notes use it), **Edit** opens the FM voice editor (for a file voice, Apply / Done write the file), **Name** renames a file voice (six characters), **→DAT** moves a MUC voice into the file under the same number, **→MUC** copies a file voice into the MUC as a definition, **Import** takes voices from `.dat`, `.muc`, `.mub` and `.vgm` / `.vgz` files and adds the ones the bank does not have yet after the others, **Load** uses a `.dat` file for the song and **Save** downloads the file (made from the MUC's voices when there is none); **↶** undoes changes to the file. *To* picks whether added and imported voices go into the file or the MUC; a song without a file gets a new `VOICE.DAT` and a `#voice` tag when the first voice goes there. The file is kept with the song's attached files, so Play uses the changes at once. From a VGM the voice of every key on is taken (YM2203, YM2608, YM2610, YM2612; YM2151 converted, without DT2 and LFO settings), the same voice at different volumes counted once, with the carriers' levels kept relative to the loudest, most used first. The voice file format (`voice-bank.js`) was checked against the compiler: a song plays the same with its voices written into a file as defined in the text. The **SCC** tab does the same for MUCOMSX's SCC waves (`SCCA`–`SCCE`): the wave file the song uses (`#sccvoice`, `SCCVOICE.DAT` by default; the SCWD format with its CRC, up to 256 waves `@W0`–`@W255`, checked against MDPlayer4Mac's compiler: a song plays the same with its waves moved into the file) and the MUC's own `@Wn:{…}` waves, each with a small picture and its shape (sine, saw, square, pulse, triangle) and how many notes use it; **Edit** opens the SCC wave editor; **Import** takes waves from `.dat` (SCWD), `.muc`, `.vgm` / `.vgz` (what the K051649 / K052539 plays at each key on) and Furnace `.fur` / `.fuw` (32-sample wavetables). A wave file with no waves left is removed with its `#sccvoice` tag.
- **Picking several, and keys, in the bank:** Ctrl / ⌘ + click adds an entry to the ones picked (or takes it out), Shift + click or Shift + ↑↓ picks a range, Ctrl / ⌘ + A all of them, Esc one again; **Del** removes all the picked entries at once (asking first, one undo step for the file), **→DAT** moves them all into the file and **→MUC** copies them all into the MUC, and imported entries come out picked. With the focus in the bank (it gets it when the bank opens; **F6** goes between the text and the bank) every button has a key: Insert / N add, Delete del, Enter / E edit, F2 / R name, D →DAT (→BIN), M →MUC, I import, L load, S save, U or Ctrl / ⌘ + Z undo, Space / P listen, @ write `@n` at the text's caret, T switch *To*, B empty slots, 1 / 2 / 3 the FM / SCC / PCM tabs, and **?** lists them.
- **Tooltips:** every button and control has a tooltip saying what it does, what it works on and its key, in English, Korean and Japanese (`tooltips.js`); the bank's are worded for the tab it shows (voices, waves or samples, and their file).
- **PCM bank:** **🥁 PCM bank** opens the **PCM** tab for the ADPCM part (`K`): the song's samples `@1`–`@32` from its PCM bank file (`#pcm`, or `mucompcm.bin`, which the compiler looks for when there is no tag; marked `BIN`) or from the MUC's own `#@pcm n,"name","file.wav",volume[,R]` lines (mucomDotNET's tag: the compiler encodes the WAV itself; any `#@pcm` line and it ignores the whole bank file, so **→BIN** moves all of them into the file and adding to the MUC first copies the file's samples there), each with its waveform, length, size and how many notes use it, and the bank's size out of the chip's 256 KB. Click a sample to hear it as the chip plays it. **Import** takes `.wav` (any PCM / float WAV, mixed to mono, brought down to 16.1 kHz when it is higher), audio the browser can decode (mp3, ogg, flac …), PCM banks, `.mub` (the bank inside) and `.vgm` / `.vgz` (the samples keyed on by a YM2608 (RAM filled by data blocks or register writes), YM2610 (ADPCM-B, and ADPCM-A decoded) or Y8950 / MSX-AUDIO, taken as they are); **Load** uses a bank file, **Save** downloads it. **Edit** opens a PCM sample editor after Furnace's sample editor: the waveform (drag to select, wheel to zoom, *Zoom to selection* / *Fit*), name and volume, **Trim**, **Delete**, **Silence**, **Fade in / out**, **Normalize**, **Amplify %**, **Reverse**, **Invert**, **Remove DC**, **Resample to** o1 c (16.1 kHz) / o2 c (8.1 kHz) / o3 c / any rate, undo / redo, and **▶ Listen** to the selection at its own rate or at a note's speed, optionally *as the chip* (encoded to ADPCM-B and decoded again). The editor shows the note that plays the sample at its own pitch (the driver plays o1 c at 16.1 kHz and each octave up at half the speed). ADPCM-B loses detail, so edits start from the audio a sample was imported from while the page is open, and Apply encodes it again; for a `#@pcm` sample Apply rewrites its WAV (16-bit mono) and line. The codec and the bank format (`pcm-bank.js`) were checked against mucomDotNET: its ADPCM-B encoder gives the same bytes, and all 40 sample songs with a PCM bank play bit for bit the same with their bank read and written again (MUCOM88 form or mucomDotNET's `mda ` form). Entries are kept exactly as the driver plays them (one 4-byte unit past the stored length, overlapping entries copied apart), and a bank written here names every entry up to the last one, because the driver skips nameless ones when it numbers them.
- **Share:** **🔗 Share** makes a link to the song as it is, like a video link: whoever opens it gets the same song and its voice / PCM files in their own browser, ready for Play. A repository sample opened as it is gives a short link (`?sample=Muc/…/SONG.muc`), an unedited built-in example `?ex=demo` / `?ex=template`. Anything else is put inside the link (`#s=…`): the text, compressed (deflate), with the repository path of every attached file that came from the repository (they load from there) and the bytes of small files of your own (up to 24 KB in all); a file that is too large or not attached is listed as not in the link. The dialog shows the link with **Copy** (and the system's share sheet on phones), says what is in it, and warns above 8,000 characters, where some messengers cut links. The page has no server: nothing is uploaded, the link itself is the song (`share.js`). Opening a link cleans the address at once, so a reload keeps what you do next; if you had your own song open it is kept aside, and **Bring it back** restores it with its files. Only paths inside `Samples/` are followed.
- **Manual mode:** **📖 Manual** under the editor splits it side by side: the MUC text on the left, an MML guide on the right (stacked on narrow screens). At the top you first pick the book: **MUCOM88** (song layout, tags, notes and lengths, tempo, volume, voices and sound, effects, repeats and macros, rhythm and ADPCM) the **mucomDotNET extensions** (the extended format, pages and branches, macros, FM volume modes, KD, MT and morphing, FM3 special mode, SSG hardware envelope, moving pan and per-drum control, MIDI-style portamento, port register writes, and what MUCOMSX adds: MSX-MUSIC, the MSX PSG, `#SSGExtend`, `#PCMInvert` and the SCC parts) or the **MucoMSX chip extensions**, the two-letter `?` commands of MDPlayer4Mac v0.2.4 and later (how they are written: compact `?XU` rows ending in `!`, `$hex`, the shared `PSGS` / `SCCS` / `OPLS` rows and braced `@n:{…}` voices; global resources; envelopes `?EP ?EA ?ET ?EN ?EL`; pitch `?DB ?DW ?DR ?DS ?MV ?MW ?KT`; gate and note end `?QR ?QP ?QE`; PSG noise and hardware envelope `?NP ?GS ?GH ?GL`; SCC waves `?WP ?WM ?WI ?WF ?WE ?WG`; MSX-MUSIC `?IR ?IU ?IS ?ID ?IT ?IB`; shared phrases `?FD ?FC ?FR ?FJ ?FB`; effects and programs `?XD ?XM ?XP ?XI ?XS ?XT ?IM ?XH ?XC ?XR ?VF`). Chapters are buttons under the search box, and the one being read is marked; the search looks through the commands, forms, explanations and examples, and points to the other books when the words are there. Each entry shows the command, its form, what it does, notes, and an example coloured like the editor; **Insert** puts the example into the song (a part line, tag or voice below the caret's line). With **Follow caret** on (the default, remembered), the guide follows the editor: the command or keyword at the caret is looked up in the context of its line (`manual-lookup.js`), the guide switches to the book that has it, scrolls to its entry and outlines it. So `@` leads to FM voices on an FM part, to the SSG presets on D E F, to the drums on G or `MSXG`, to the samples on K and to the waves on an SCC part; `v` on G with seven values to the rhythm volumes, with one value to the per-drum extension; `S` on C to the slot detune, on SSG to the hardware envelope. Tags, macro definitions, FM voice and SCC wave definitions, part prefixes (`A0`, `ABC`, `MSXA`, `SCCA`, `PSGS` …), notes and every command of the three books are recognised; `?EP2,129,115`, `?FD1={…}` and the other `?` commands lead to their MucoMSX entries, a resource line such as `?WD0={…}` to its definition, `  @1:{…}` to the braced voice. The guide is written for this page in English, Korean and Japanese and follows the page language; its text is in `manual-data.js` (every example compiles), the view in `manual.js`. *Text* sets the text size of the guide's contents only (10–24 px; the book buttons, search and chapter bar keep their size, and the editor has its own; double-click it for the default, which follows *Menus*). The chosen book, the text size and the mode are remembered.
- **Quick reference:** the side panel lists every entry of the guide, all three books, one short row each (command and title) grouped by chapter, in a list that scrolls by itself (`quick-ref.js`). It follows the caret the same way the manual does: the command or keyword at the caret is marked, scrolled into view inside the list (the page does not move) and opened up to show its form; this works with or without manual mode. *Filter* narrows the list, hovering a row shows its form and explanation, and clicking it opens that entry in manual mode, even with *Follow caret* off.
- **Keys mode:** the **🎹 Keys** button under the editor opens a piano under the text (three octaves, **−** / **+** or `↑` / `↓` to move them). Click or touch the keys (slide across them), or click the piano once and play it from the computer keyboard, tracker style: `Z S X D C V G B H N J M` for the lower octave, `Q 2 W 3 E R 5 T 6 Y 7 U I 9 O 0 P [ = ]` for the ones above; the PC key is printed on each piano key. Typing in the editor stays typing: the keys only listen while the piano has the focus. *Sound* follows the part the caret is in: its FM voice (the last `@n` of that part, from an inline definition; otherwise a default voice), its SCC wave (`@n` → `@Wn`), the SSG / PSG square, or noise for rhythm parts; any inline FM voice or SCC wave of the song can also be picked. The keys have their own low-latency audio and synthesizer (`keys-worklet.js`: four OPN operators with the envelopes of the FM preview, or the 32-step wave), a sketch for trying notes rather than the chips' emulation; Play still uses the real chips.
- **Play one line:** with the caret on a part line that has notes, a **▶** appears at the end of the line; it plays just that line (`Ctrl+Shift+Enter` does the same, and with several lines selected it plays those lines). The line starts with the settings its part has at that point in the song: earlier lines of every part keep their commands (voice, volume, octave, length, tempo, envelopes …) and lose their notes, rests, ties and repeats; later lines are left out; a repeat or loop point that starts or ends outside the played lines is ignored. Every line stays in place, so the playing position is highlighted on your own text. While it plays the button turns into **■** to stop. Repeats outside the line are followed only once, so a part that changes octave inside an unbalanced repeat can start an octave off.
- **Channel view, as in MDPlayer4Mac:** while a song plays, **▦ Channels** swaps the editor for MDPlayer4Mac's channel view: each chip's panel (YM2608, YM2610, YM2203, YM2151, YM2413, AY-3-8910 PSG, K051649 SCC/SCC+) with a keyboard per channel, note names, frequencies, level meters, pan, voice registers and, for the SCC, the wave tables, drawn with MDPlayer's own bitmaps. The chips the song uses are named at the top left in MDPlayer's note font (`YM2608`, `AY8910  YM2413  K052539`, the same chip twice as `YM2610 X2`). Panels are stacked FM → SSG/PSG → PCM, rows are grouped the MDPlayer4Mac way, the rhythm / ADPCM meters follow the emulator's real output, and **Size** opens at *Fit* each time the view is shown and goes back and forth, *Fit* → 100 → 75 → 50 → 25 → 50 → 75 → 100 % → *Fit* …; *Fit* scales the panels, keeping their shape, to the largest size at which all of them fill the view, and follows the window as it is resized. Playing a `.mub` or `.vgm` switches to it by itself; playing a MUC afterwards returns to the editor. Stopping keeps the panels on screen. The view follows what you hear: the engine logs every chip write with its audio frame (for VGM files the page reads the writes from the file), and they are applied as that frame is played.
- **Split editor:** the **Split** buttons under the editor show the song twice, side by side or one above the other, to work on two places of a long MUC at once. Both views are live; typing in either changes both. While a song plays, the view you are working in stays where it is and the other one follows the playing part. Drag the bar between them to resize (double-click to even them); the choice is remembered.
- **Examples:** a short demo with inline FM voices, and **Samples…**, a browser for this repository's [`Samples`](../Samples) folder (search, grouped by folder; `.muc` opens in the editor, `.mub` / `.vgm` / `.vgz` play). Its first groups are the [templates](../Samples/Muc/Templates): basics, one per sound chip, drum libraries, genre songs with drums, bass and chords ready for your melody, and *Midnight Pier*, a finished city pop demo that plays every chip at once, commented in English and Japanese. The folder is read live from GitHub, so **a song committed to `Samples/` shows up straight away**, without rebuilding anything. Voice / PCM files the song names (for example `SNATCHEA.DAT`) are fetched from the same folder. The list is cached for 10 minutes (*Refresh* rereads it); if GitHub cannot be reached, for example after GitHub's limit of about 60 anonymous API requests an hour, the list built into the page (`samples.json`) is used instead.
- **New:** starts a song from the template (`template.muc`, the same as `Samples/Muc/Templates/2_Chips/OPNA_and_MSX_All.muc`, with comments in English and Japanese, also in the examples list as *Template (OPNA + MSX chips)*), an 8-bar song that uses OPNA and every MSX target of the latest msPb format together, with a comment on each part: OPNA FM (inline voices), OPNA rhythm, MSX-MUSIC (`MSXA`/`MSXB` and the `MSXG` drums), the MSX PSG (`MSXD`, with a software envelope) and the five SCC/SCC+ parts `SCCA`–`SCCE` (inline `@Wn:{…}` waves, envelopes, macros, repeats with `/`, the `L` loop). Attached files are removed. New asks first when the editor holds your own text; the template counts as yours from the first keystroke.
- **Your own files:** open a `.muc`, attach `#voice` / `#pcm` files, or drop them on the page. Your song is autosaved in the browser **together with its attached voice / PCM files** (IndexedDB), so after leaving and coming back it plays exactly as before. If a restored song names a file that was not kept (for example one saved by an older version of the page), it is fetched again from the song's Samples folder, or from `Samples/` when exactly one file there has that name.
- **Channel volume in the channel view:** for songs the MUC engine plays (MUC and .mub), a column of faders beside the chip panels, one on each channel's own row, drawn with MDPlayer4Mac's mixer graphics (its `rFader` rail, knob and level bar, turned on their side as its mixer does, and the `rFont_03` digits): OPNA FM1–6, SSG1–3, ADPCM and the six rhythm sounds; YM2610 FM, SSG, ADPCM-B and ADPCM-A 1–6; OPM 1–8; OPLL 1–9 and its five drums; PSG A–C; SCC 1–5. The faders use MDPlayer4Mac's mixer units (0.5 dB steps, 0 — the song's own level — 35/43 of the way along as MDPlayer's fader has it, values printed as MDPlayer prints them): from −32 (−16 dB) to +20 (+10 dB), and OFF below −32. Dragging rests at 0 for a couple of pixels on the way through; the small key at the right of each fader puts it back to 0; the wheel moves it 0.5 dB (from −32 down to OFF), clicking the number switches the channel off and back, double-clicking a fader returns it to 0 and double-clicking VOL returns the whole chip. **RESET VOL**, lined up with the faders (same position, width and height) two rows below the last one, puts every channel of every chip back to 0 (channels switched OFF too; it is dimmed when there is nothing to reset, and leaves the toolbar's Volume as it is). The emulators mix their channels inside, so the engine (`ChannelMixer.cs`) applies the faders to the registers the song writes, as a driver sets volume: the carrier operators' TL by the channel's algorithm (0.75 dB steps), the SSG / PSG / OPLL / SCC volume (about 3 dB steps; a channel on the SSG hardware envelope can only be switched off), each rhythm / ADPCM-A sound's level, and the ADPCM-B level; louder goes only as far as a register can (a carrier already at full level, or SSG at 15, stays). Checked natively: −24 (−12 dB) measures −12.1 dB on FM (algorithms 0 and 7) and SSG, −60 measures −30 dB, +10 measures +5 dB where there is headroom, OFF is silent, and switching off the ADPCM or all SCC channels gives exactly the song without those parts (OPLL's quietest level is −45 dB, so its OFF leaves a faint trace). The settings stay for the next songs; the chip panels still show the song's own register values, and saved .mub / .vgm files are unchanged. VGM files play on MDPlayer's own player, which has no per-channel volume, so they show no faders.
- **Playback speed:** the **Speed** slider beside Volume plays the song at 25–200 % without changing its pitch: the MUC engine runs the driver's timers that many steps per output sample, and VGM files use MDPlayer's own VGM speed. While dragging, the slider rests at 100 % for a few pixels (a small mark under the track shows where), so normal speed is easy to find again; double-click goes back to 100 %, and the arrow keys move it 1 % at a time. The value shows in colour when it is not 100 %. Saved .mub / .vgm files are always at normal speed.
- **A song with its files:** a page cannot read the files next to a file you open, so there are three ways to bring a song's voice / PCM files with it. **Open…** takes several files at once: pick the `.muc` together with its `.dat` / `.pcm` / `.bin` / `.wav` files (Ctrl / ⌘ or Shift + click) and they are attached before the song opens. **Folder…** opens a folder on your computer and lists its songs (search by name, grouped by sub-folder; a folder with one song opens it at once); opening one attaches every file it names (`#voice`, `#sccvoice`, `#pcm`, `#@pcm`, and `voice.dat` / `mucompcm.bin` / `SCCVOICE.DAT` next to it when it names none), found by name whatever their case: next to the song first, else the only file of that name in the folder. Chrome and Edge remember the folder (one permission click next time); Safari and Firefox read the folder they are given each time. A folder dropped on the page does the same. Once a folder is open, a song opened from it by itself (Open…, drop) takes its missing files from there too. And when a file the song names is not attached, Compiler messages say so (warning PG03, what goes missing from the song: the K part's samples, voices or waves), with **Attach file…** and **Find in folder** buttons; the files card lists it as not attached as before. (`local-folder.js`)
- **Play `.mub`, `.vgm` and `.vgz` files** with **Open…** or by dragging them from your computer onto the page. A dropped `.muc` opens in the editor and starts playing; voice / PCM files dropped with it are attached first. `.mub` plays on the editor's engine. `.vgm` / `.vgz` play on MDPlayer4Mac's own VGM player, which is downloaded the first time you play one (about 20 MB, 7.3 MB compressed) and sounds sample-for-sample like the desktop app.
- **SCC wave preview:** with the caret on a wave definition, the wave is drawn under it: `@Wn:{…}` with 32 samples for `SCCA`–`SCCE`, or `@Wn` followed by rows of 64 samples for `#SSGExtend` (`$00`–`$FF` too), one or several lines, read the way MDPlayer4Mac reads them. It updates while you type, shows the number of samples and their range, and marks a wrong count, unreadable values or values outside -128..127 in red.
- **SCC wave editor:** the wave preview has an **✎ Edit** button that turns the editor area into a wave editor modelled on [Furnace](https://github.com/tildearrow/furnace)'s wavetable editor: draw the wave with the mouse or a finger (Steps or Lines view), or generate it on the *Shapes* tab (sine / triangle / saw / pulse with duty, exponent, XOR point and 16 harmonics with amplitude and phase) or the *FM* tab (four operators with level, multiplier, feedback, Furnace's 32 operator waveforms and a connection matrix), then reshape it with *WaveTools* (offset X / Y, smooth, amplify, normalize, invert, reverse, half, double, randomize, clear). The values can also be typed in decimal or hex, **▶ Listen** plays the wave as a held note (o2–o6), and undo / redo (Ctrl+Z / Ctrl+Y) cover every change. **Apply** writes the definition back into the song as one `@Wn:{…}` line (or `@Wn` and four rows for a 64-sample `#SSGExtend` wave, keeping a trailing comment), **Done** applies and returns to the text, **Cancel** returns without writing. Play while the editor is open applies first, so you hear what you drew.
- **FM voice preview:** with the caret on an inline FM voice (`  @n`, its `FB,ALG` line or one of the four operator lines), a panel under the voice shows the algorithm (operators, which ones are heard, OP1's feedback), the output wave and each operator's envelope (AR, D1R, D1L, D2R, RR, with TL added; key on for 1 s, then key off), in one colour per operator; the operator line the caret is on is drawn bold. It updates while you type and lists a wrong number of values or values out of range. Voices in MUCOM88's 25-byte form (`  @%n`: six lines of four register values in slot order, decimal or `$hex`, then FB/ALG) are read too and shown the same way; they are edited in the text (the *Edit* button is not offered, since the FM editor writes the usual form). Songs saved with CRLF line ends are read like any other. The wave is computed the OPN way (phase modulation, TL in 0.75 dB steps, ML, feedback) at full envelope level without DT and KS, and the envelope times follow the OPN rate table roughly: a guide for editing, not an emulation.
- **FM voice editor:** the FM voice preview has an **✎ Edit** button too, which opens an OPNA voice editor modelled on [Furnace](https://github.com/tildearrow/furnace)'s FM instrument editor: the overview (algorithm, output wave, envelopes), the eight algorithms as pictures to pick from, OP1's feedback, and a card per operator with Furnace's controls in its order — AR, DR (D1R), SL (D1L), D2R, RR, TL, KS (Furnace's RS), MULT (ML), DT — as sliders with number boxes, its envelope drawn the way Furnace draws it, whether it is a carrier or a modulator, and a warning when a carrier's TL is not 0 (W0408). Operators can be copied and pasted, *Init* starts from Furnace's default FM voice, the five lines can also be typed, and undo / redo cover every change. **▶ Listen** plays one note (o1–o7) with an approximate render in the page (phase modulation, envelopes with key scaling; no DT or LFO); Play in the toolbar applies the voice first and plays the real chip. **Apply** / **Done** write the `FB,ALG` line and the four operator lines back, keeping their layout (`31,0,0,7` packed or `  31,  8,  3` padded), indents and comments.
- **Silent parts:** besides the compiler's messages, the page warns about a part that compiles but cannot make a sound: an SSG / PSG part (`D E F`, `MSXD`–`MSXF`) with no `@` or `E` (or hardware envelope `S`) before its first note, and an SSG, PSG, SCC or `MSXG` part with no `v` (MUCOM88 starts them silent). The warnings (PG01, PG02) mark the first note's line like any other warning.
- **Save** (or `Ctrl+S`) writes the song to your computer as `.muc` in Shift-JIS, for samples as well as your own songs. If the text holds characters Shift-JIS cannot (Korean, emoji …), the page lists them and asks first, because they would be saved as `?`; the buttons next to it save `.muc` (Shift-JIS with CR+LF, ready for the MSX), `.mub` or `.vgm`:
  - `.mub` is the playground compiler's output, the same as MDPlayer4Mac produces from that MUC. It is not byte-for-byte what MUC2MUB on the MSX writes, so check it on the machine before relying on it there.
  - `.vgm` (VGM 1.71) logs every chip write. A looping song is written as intro + one more pass, with the VGM loop point set so the loop is exactly one pass; songs are capped at 10 minutes. Played back in MDPlayer4Mac it matches the playground's own audio (correlation 1.0000 on the test songs).
- What you type is kept in your browser between visits. Nothing is uploaded anywhere.
- Plays YM2608 (FM, SSG, rhythm, ADPCM), the extended `muPb` layouts, and the MUCOMSX native MSX parts: MSX-MUSIC, PSG, SCC/SCC+, including the five dedicated SCC/SCC+ parts `SCCA`–`SCCE` of msPb0102 (MDPlayer4Mac v0.2.3) with inline `@Wn:{…}` waves and `#sccvoice` wave banks, and the MucoMSX chip extension commands of MDPlayer4Mac v0.2.4 and later (`?EP`, `?FD`, `?WD` … compiled into the packed msPb0103–010A score and played by MDPlayer4Mac's native MSX session, alone or together with OPNA).

**iPhone / iPad:** sound starts with a tap (Play, or a tap anywhere when the page asks). The page registers as a media player, so it plays even with the ringer switch or iPad silent mode on (Safari 17's `navigator.audioSession`, or a silent looping track on older iOS). The engine needs iOS / iPadOS 16.4 or later (WebAssembly SIMD and exception handling).

## How it works

The sound engine is not a new implementation. It is **[MDPlayer4Mac](https://github.com/ToughkidDev/MDPlayer4Mac)'s** MUC path compiled ahead of time (AOT) to WebAssembly with .NET 8:

| Part | Source |
|---|---|
| MUC compiler | mucomDotNET compiler with MDPlayer4Mac's MUCOMSX changes |
| MUCOM88 driver | mucomDotNET driver with MDPlayer4Mac's MSX overlay |
| MSX parts | MDPlayer4Mac's `MucoNative` (`NativeMucCompiler`, `MsxMucCompiler`, `MsxMusicalCompiler`, `NativeMucomSession`, `PackedMusicPlayer` …) |
| Chip emulation | MDSound (fmgen YM2608/YM2610/PSG, emu2413, K051649, YM2151) |

`src/Engine/MucEngine.cs` is the only new engine code: it wires those pieces together the
way MDPlayer4Mac's `MusicEngine` and `MucomDotNET` adapter do, without the desktop UI.
Songs with the MucoMSX chip extensions (packed msPb0103–010A) play through `NativeMucomSession`,
whose chip writes `MucEngine` routes to the same chips, so the channel view, the faders and
`.vgm` export work for them as for any other song.
`src/Engine/ChannelMixer.cs` applies the channel view's faders to the chip registers.
`src/Engine/MsxTrace.cs` recovers the source positions of MUCOMSX songs for the playback
highlight: `MsxMucCompiler` rewrites the text and packs the result into an msPb container,
so the same steps are repeated with a map from each rewritten line back to the editor's line,
and the compiler's data (which carries the positions) is laid over the packed pages whose
bytes match (packed scores are not traced: the playback highlight is off for them). Playback is unchanged: all 12 MUCOMSX templates render identically with and
without it.
Rendered output is checked to be **sample-for-sample identical** to MDPlayer4Mac's
EngineSmokeTest for its 20 MSX regression songs and a Gradius sample, both natively and
in Chromium.

The page runs the engine in a Web Worker and streams audio to an AudioWorklet about one
second ahead. The engine is AOT-compiled, which renders about 7× faster than .NET's
WebAssembly interpreter with sample-for-sample the same output. In headless Chromium on a
modest 4-core server it renders an OPNA song about 16× faster than real time and the
template, which runs OPNA and all the MSX chips at once, about 6× (the YM2413 emulation is
the heaviest chip); the interpreter managed 2.2× and 0.6×.

## Rebuilding the engine

```sh
dotnet workload install wasm-tools   # .NET 8 SDK
MUCPlayground/src/build.sh
```

`build.sh` checks out MDPlayer4Mac at the pinned commit, publishes `src/Web` and
`src/VgmWeb`, and copies only the files the browser loads into `engine/` (about 11 MB, 4.2 MB
compressed) and `engine-vgm/` (about 20 MB, 7.3 MB compressed); AOT compilation takes a
few minutes. Run it again after
adding samples to refresh `samples.json`.

To compare against MDPlayer4Mac on the desktop:

```sh
dotnet run -c Release --project MUCPlayground/src/NativeCheck -p:Mdp4MacDir=<MDPlayer4Mac checkout> -- song.muc out.wav 60
```
