# MUC2MUB 사용설명서

MSX에서 MUC를 MUB로, 한 곡씩 차근차근.

이 설명서는 **MUC2MUB v3.15**를 기준으로 작성했습니다. 기준일은 2026년 9월 15일이며, 프로젝트의 최신 표준 실행 파일인 `bin/muc2mub.com`을 대상으로 합니다.

MUC2MUB는 MUCOM88의 MML 소스인 `.MUC` 파일을 MSX에서 컴파일하여 `.MUB` 파일로 저장하는 프로그램입니다. 곡을 수정한 뒤 결과물을 만들 때도 쓰고, 여러 곡을 DOS 배치 파일로 차례대로 변환할 때도 쓸 수 있습니다.

기본 사용법 자체는 간단합니다.

```dos
MUC2MUB SONG.MUC
```

그러면 `SONG.MUB`가 만들어집니다. 다만 실제 곡을 다루다 보면 음색 파일, PCM 파일, 파일명, 메모리, 저장 공간 때문에 헷갈리는 부분이 생깁니다. 이 설명서에는 그런 부분까지 함께 정리했습니다. 처음부터 모든 내용을 외우실 필요는 없습니다. 먼저 한 곡을 변환해 보고, 필요한 항목을 찾아 읽으시면 됩니다.

## 1. 어떤 프로그램인가

MUC는 음표와 명령을 글자로 적어 놓은 소스 파일입니다. MUB는 그 내용을 재생 드라이버가 사용할 수 있도록 변환한 바이너리 파일입니다.

MUC2MUB의 역할은 이 둘 사이의 변환입니다. 기준이 되는 문법은 **MUCOM88 v1.7 계열**이며, 출력은 **MUB8 형식**입니다.

- MUC를 편집하는 프로그램은 아닙니다.
- 곡을 직접 재생하거나 녹음하는 프로그램도 아닙니다.
- WAV나 MP3를 만드는 프로그램이 아닙니다.
- 아무 MML 파일이나 MUCOM88용으로 자동 변환하는 프로그램은 아닙니다.
- 현대의 모든 MUCOM88 확장 문법을 지원한다는 뜻도 아닙니다.

다른 컴파일러용 소스이거나 새로운 드라이버 전용 명령이 들어 있는 곡은 문법과 재생 환경을 따로 확인해야 합니다. 확장자를 `.MUC`로 바꾸는 것만으로 호환되지는 않습니다.

## 2. 실행 환경과 준비물

### 실행 환경

| 항목 | 기준 |
|---|---|
| CPU | Z80에서 실행 가능. R800 전용 프로그램이 아님 |
| 운영체제 | MSX-DOS 2 및 매퍼 서비스를 제공하는 환경. Nextor 구성 검증 |
| 메모리 | MegaFlashRom SCC SD나, Carnivore2와 같이 512 KiB 이상 매퍼 구성을 장착한 sd카트리지와 사용 기준을 권장. 실제로 할당 가능한 여유 세그먼트가 필요 |
| 저장 매체 | DOS에서 읽고 쓸 수 있는 매체. 입력·자산 읽기와 출력 폴더 쓰기가 가능해야 함 |
| 실행 파일 | `MUC2MUB.COM` |
| 소스 | MUCOM88 v1.7 계열의 `.MUC` |
| 추가 파일 | 곡에 필요한 FM 음색 데이터 및 PCM 데이터 |

512 KiB 이상의 구성에서 검증했습니다. 하지만 현재 프로그램은 설치 RAM이 정확히 몇 KiB인지를 기준으로 일괄 허용·거부하는 방식이 아닙니다. DOS 매퍼를 통해 필요한 작업 세그먼트를 할당할 수 있어야 합니다. 자세한 내용은 [메모리 제한](#11)을 보시면 됩니다.

DOS 1이나 BASIC에서 직접 실행하는 사용법은 지원 대상으로 안내하지 않습니다. 먼저 DOS 2 계열 환경으로 부팅해 주십시오.

컴파일 자체에는 곡을 재생할 음원 장치가 필요하지 않습니다. 다만 완성된 MUB를 제대로 들으려면 별도의 호환 플레이어와 음원 환경이 필요합니다. MSX의 기본 PSG만으로 OPNA의 FM·리듬·ADPCM까지 모두 재생되는 것은 아닙니다.

### 파일 준비

처음에는 한 폴더에 필요한 파일을 모아 두는 편이 가장 간단합니다.

```text
MUC2MUB.COM
SONG.MUC
VOICE.DAT       곡에서 외부 FM 음색을 사용할 때
MUCOMPCM.BIN    곡에서 기본 이름의 PCM 데이터를 사용할 때
SONG.MD5       원문 해시를 넣으려는 경우에만
```

`VOICE.DAT`와 `MUCOMPCM.BIN`이 모든 곡에 무조건 필요한 것은 아닙니다. 곡 안에 FM 음색이 정의되어 있거나 PCM 채널을 사용하지 않는 곡도 있습니다. 반대로 해당 파일을 실제로 사용하는 곡이라면, 이름만 같은 다른 파일을 가져와서는 안 됩니다.

실행할 때 `.ASM`, `.SYM`, Java, 어셈블러는 필요하지 않습니다. 일반 사용자는 최신 `MUC2MUB.COM`을 MSX에서 보이는 디스크로 복사하면 됩니다.

## 3. 처음 한 곡 변환하기

### 이미 가지고 있는 곡으로 시작하기

1. 원본 MUC와 음색·PCM 파일을 별도로 백업합니다.
2. MSX-DOS에서 곡이 들어 있는 드라이브와 폴더로 이동합니다.
3. 아래처럼 실행합니다.

```dos
MUC2MUB SONG.MUC
```

출력 이름을 직접 정하려면 다음처럼 입력합니다.

```dos
MUC2MUB SONG.MUC TEST.MUB
```

처음 시험할 때는 `TEST.MUB`처럼 다른 이름으로 저장해 두면 원래 가지고 있던 MUB와 비교하기 좋습니다. 정상적인 기존 출력 파일은 별도의 덮어쓰기 질문 없이 새 결과로 교체되므로, 원본 MUB를 비교 자료로 쓰고 있다면 특히 주의해 주세요.

실행 중에는 버전 배너와 `Compiling:`, `Used FM voices:`, `Writing  :` 등의 진행 표시가 나오며, 정상적으로 마치면 다음 문구가 표시됩니다.

```text
Done.
```

여기서 끝내지 말고, 앞쪽에 경고가 있었는지도 확인해 주세요. `Done.`은 변환과 저장 절차가 끝났다는 뜻이지, 원래 곡에 필요한 외부 파일까지 모두 올바르다는 보증은 아닙니다.

### 작은 시험용 MUC 만들기

일반 텍스트 편집기에서 아래 내용을 `TEST.MUC`로 저장해 보세요. 코드 블록의 테두리는 넣지 않습니다.

```muc
#title FIRST TEST
#composer MY NAME
#comment Simple SSG test
D o4 l4 v12 cdefgab>c
```

```dos
MUC2MUB TEST.MUC
```

이 예제는 D 채널, 즉 SSG를 사용하므로 외부 FM 음색이나 ADPCM을 이용하지 않습니다. 현재 버전은 PCM을 사용하지 않는 곡에서도 기본 PCM 파일을 찾는 과정에서 누락 경고를 표시할 수 있습니다. 이 예제처럼 K 채널을 사용하지 않는다면 그 경고 때문에 PCM을 새로 준비할 필요는 없습니다.

`TEST.MUB`가 만들어졌으면 호환 플레이어에서 들어 보십시오. 소스 작성 → 컴파일 → 결과 확인의 기본 흐름은 이것으로 충분합니다.

## 4. 명령어와 파일명 규칙

### 기본 형식

```text
MUC2MUB 입력파일 [출력파일]
```

대괄호는 “생략할 수 있다”는 뜻입니다. 실제 명령에 `[`와 `]`를 입력하는 것이 아닙니다.

```dos
MUC2MUB SONG.MUC
MUC2MUB SONG.MUC RESULT.MUB
MUC2MUB SONG.MUC OUT\RESULT.MUB
```

마지막 예제의 `OUT` 폴더는 미리 존재해야 합니다. 프로그램이 출력 폴더를 자동으로 만들지는 않습니다.

출력 이름을 생략하면 입력 이름의 확장자를 `.MUB`로 바꿉니다. 입력 이름에 드라이브를 명시했다면 자동 출력 이름에도 그 드라이브 지정이 이어집니다. 다른 곳에 저장하고 싶다면 출력 위치를 직접 지정하세요.

### 입력 파일명

입력은 다음 규칙을 따릅니다.

- 본 이름은 1~8자, 확장자는 사용할 경우 1~3자입니다.
- 영문자, 숫자, 밑줄 `_`, 하이픈 `-`를 사용합니다.
- 영문 대소문자는 구분하지 않습니다.
- `A:SONG.MUC`처럼 드라이브를 붙일 수 있습니다.
- 하위 폴더 경로, 공백, 따옴표, 와일드카드는 지원하지 않습니다.
- 긴 이름을 자동으로 줄여 다른 파일을 여는 방식은 사용하지 않습니다.

| 예 | 사용 여부와 설명 |
|---|---|
| `SONG.MUC` | 가능 |
| `BOS010.MUC` | 가능 |
| `MY_SONG.MUC` | 가능 |
| `A:SONG.MUC` | 가능. 자산 탐색 위치까지 바뀌는 것은 아님 |
| `LONGSONG1.MUC` | 불가. 본 이름이 9자 |
| `MY SONG.MUC` | 불가. 공백 포함 |
| `"MY SONG.MUC"` | 불가. 따옴표로 감싸도 해결되지 않음 |
| `ALBUM\SONG.MUC` | 입력 인수로는 불가. 먼저 `CD ALBUM` |
| `*.MUC` | 불가. 여러 파일을 한 번에 받는 기능이 아님 |
| `곡이름.MUC` | 사용하지 않음. DOS용 ASCII 이름으로 준비 |

확장자는 혼동을 피하도록 입력 `.MUC`, 출력 `.MUB`로 통일하는 것이 좋습니다.

### 출력 파일명

출력은 DOS 경로를 붙일 수 있습니다. 다만 마지막 파일명은 위와 같은 8.3 규칙을 따릅니다. 입력과 출력의 경로 지원 범위가 다르다는 점을 기억해 주세요.

인수 하나는 최대 63바이트이고, 출력의 드라이브·디렉터리 접두부는 임시 파일 이름을 붙일 공간 때문에 최대 52바이트입니다. 긴 경로를 시험하기보다는 가까운 폴더를 출력 위치로 사용하세요. DOS 명령줄 전체 길이 제한도 별도로 적용됩니다.

입력과 출력의 **마지막 파일명 전체가 같으면** 다른 드라이브나 폴더라 하더라도 거부합니다. 예를 들어 `SONG.MUC`를 `OUT\SONG.MUC`로 출력하는 것은 허용하지 않습니다. 원본 소스를 실수로 덮어쓰지 않도록 보수적으로 검사하는 것입니다. `SONG.MUC` → `SONG.MUB`는 확장자가 다르므로 정상적인 사용입니다.

### 지원하지 않는 호출 방식

한 번 실행할 때 입력 한 개와 선택적인 출력 한 개만 받습니다. 세 번째 파일을 추가하지 마세요.

`-o`, `/FORCE`, `/STRICT`, `/MUB`, 재귀 검색 등의 옵션은 MUC2MUB의 명령행 기능이 아닙니다. 특히 다른 프로그램의 옵션을 그대로 가져와 사용하지 마십시오.

인수 없이 실행하면 사용 형식이 나오지만, 전용 대화형 도움말 화면은 아닙니다. 또한 시작할 때 매퍼를 먼저 초기화하므로 메모리 환경이 맞지 않으면 사용법보다 매퍼 오류가 먼저 보일 수 있습니다.

## 5. 폴더와 드라이브 사용법

여러 앨범을 다룰 때 가장 주의할 부분입니다. **음색과 PCM의 상대 파일명은 현재 작업 디렉터리를 기준으로 찾습니다.** 입력 파일이 있는 곳을 자동으로 찾아 자산 탐색 기준을 바꾸는 방식이 아닙니다.

저는 곡마다 다음 순서를 지키는 사용법을 권합니다.

1. 해당 드라이브로 전환합니다.
2. 곡과 자산이 있는 폴더로 이동합니다.
3. 그 자리에서 컴파일합니다.

```dos
B:
CD \ALBUM1
MUC2MUB SONG.MUC
```

위 예제는 `MUC2MUB.COM`이 현재 폴더에 있거나 DOS의 실행 파일 검색 경로에서 발견된다는 전제입니다. 실행 파일을 찾지 못하면 현재 곡 폴더에 복사해서 먼저 시험해 보세요.

다음처럼 입력만 다른 드라이브로 지정하는 것과는 차이가 있습니다.

```dos
MUC2MUB B:SONG.MUC
```

이 명령이 B 드라이브의 곡을 읽더라도, `VOICE.DAT`나 PCM의 상대 탐색 위치가 함께 B 드라이브로 이동하지는 않습니다. “소스는 맞는데 음색이 다르다”면 이 부분부터 확인하세요.

서로 다른 앨범에 이름이 같은 `VOICE.DAT`가 들어 있는 것은 흔한 일입니다. 편하다고 모든 파일을 하나의 폴더로 합치면 한 앨범의 자산으로 다른 곡을 컴파일할 수 있습니다. 앨범별 폴더 구성을 유지하는 편이 안전합니다.

<a id="06"></a>

## 6. MUC 파일 작성과 채널

이 절은 변환을 위해 필요한 기본 안내입니다. 모든 MUCOM88 명령과 음원 레지스터를 설명하는 MML 언어 사전은 아닙니다. 복잡한 곡은 사용한 원본 드라이버의 문법도 함께 확인해 주세요.

### 텍스트 형식

MUC는 서식 없는 텍스트입니다. 워드프로세서 문서나 UTF-16 파일로 저장하지 마십시오.

영문만 있는 시험 파일은 ASCII로 준비하면 편합니다. 기존 일본어 MUCOM88 자료는 Shift_JIS/CP932 계열인 경우가 있으므로, 원본의 인코딩을 보존하세요. 현재 컴파일러는 문자 인코딩을 자동 판별·변환하는 프로그램이 아닙니다. UTF-8 BOM이나 전각 공백이 들어가면 행 머리의 명령·태그를 인식하지 못할 수 있습니다. 한글 태그 표시도 컴파일러뿐 아니라 플레이어와 표시 환경의 지원에 달려 있습니다.

CRLF, LF, CR 개행을 처리하지만, DOS 도구와 함께 쓸 때는 CRLF로 통일하면 관리하기 편합니다. 비교용 원본이 있다면 개행을 바꾸는 것만으로도 원문 해시와 태그 바이트가 달라질 수 있다는 점은 별개로 기억해 주세요.

파일 중간에 NUL이나 DOS의 텍스트 끝 표시인 Ctrl-Z가 섞이지 않도록 합니다. 화면에는 보이지 않아도 뒤쪽 내용을 읽지 못하게 만들 수 있습니다.

### 채널은 반드시 행 맨 앞에

```muc
A o4 l4 cdef
A gab>c
```

채널 문자는 대문자 `A`~`K`, 그다음에는 공백 또는 탭을 넣습니다. 같은 채널을 여러 행으로 나누어 적을 수 있습니다.

```text
A o4 c      정상적인 채널 행
 A o4 c     앞에 공백이 있으므로 잘못된 채널 행
a o4 c      소문자 채널이므로 잘못된 채널 행
A,o4 c      채널 뒤 쉼표는 구분자로 지원하지 않음
A,B c       한 행에 채널 목록을 나열하는 방식은 지원하지 않음
```

잘못된 채널 행은 경고를 내고 빠질 수 있습니다. 곡 일부가 사라진 것처럼 들릴 때에는 “컴파일 오류가 없었다”는 이유로 이 가능성을 제외하지 마세요.

### 채널 배치

| 채널 | 담당 음원 |
|---|---|
| A, B, C | FM 1, 2, 3 |
| D, E, F | SSG 1, 2, 3 |
| G | 리듬 |
| H, I, J | FM 4, 5, 6 |
| K | ADPCM |

다른 MML 시스템의 채널표와 혼동하지 않도록 주의해 주세요. 특히 D·E·F는 FM이 아니라 SSG입니다.

### 자주 쓰는 기본 표기

| 표기 | 의미 또는 용도 |
|---|---|
| `c d e f g a b` | 음표 |
| `r` | 쉼표 |
| `o4` | 옥타브 지정. `o1`~`o8` 범위 |
| `>` / `<` | 옥타브 올림 / 내림 |
| `l4` | 이후 음표의 기본 길이 지정 |
| `c8` / `r8` | 음표·쉼표의 길이를 직접 지정 |
| `v12` | 볼륨 지정. 유효 의미와 범위는 채널에 따라 확인 |
| `@1` | 해당 채널의 음색·샘플 선택. FM과 ADPCM에서 의미가 다름 |
| `[cdef]2` | 구간 반복 |
| `[c / d]2` | 마지막 반복의 탈출 위치 지정 |
| `L` | 곡 반복 위치 지정 |
| `;` | 주석 시작 |

대문자와 소문자 명령을 임의로 바꾸지 마세요. 같은 글자라도 다른 명령일 수 있습니다.

### 반복과 매크로

```muc
A o4 l4 [c d e f]2 g
```

반복의 `[`와 `]`는 짝을 맞춰야 합니다. `/`는 반복 안에서 사용하는 탈출 표시입니다. 반복 밖에 적거나 같은 반복에 두 번 넣으면 오류가 됩니다. 반복 중첩은 최대 16단계입니다.

```muc
# *1{o4 l4 cdef}
A *1 gab>c
```

위 예제에서 `# *1{...}`는 매크로 정의, `*1`은 호출입니다. 처음에는 예제처럼 짧은 매크로를 한 행에 정의해 사용하세요. 매크로 본문은 511바이트까지, 중첩 호출은 최대 4단계입니다. 자기 자신을 계속 호출하는 매크로는 사용할 수 없습니다.

매크로는 소스를 정리하는 수단이지, 언제나 결과 DATA를 줄여 주는 압축 기능은 아닙니다. 반복되는 이벤트의 크기를 줄이고 싶다면 음악적으로 같은 결과를 유지할 수 있는지 확인하면서 반복 구문을 사용하세요.

## 7. 태그와 곡 정보

제목, 작곡가, 외부 파일 지정 등은 파일 맨 위에 모아서 적습니다.

```muc
#title MY SONG
#composer MY NAME
#author MY NAME
#comment Test version
#voice VOICE.DAT
#pcm PCM.BIN
#date 2026/09/15
A @1 o4 l4 cdef
```

이 예제의 외부 파일은 실제로 준비되어 있어야 합니다.

| 태그 | 용도 |
|---|---|
| `#title` | 곡 제목 |
| `#composer` | 작곡가 |
| `#author` | 작성자 정보 |
| `#comment` | 부가 설명. 값이 비어 있어도 허용 |
| `#date` | 날짜 정보 |
| `#voice` | 외부 FM 음색 파일 이름 |
| `#pcm` | 외부 PCM 파일 이름 |

현재 경고 검사에서는 이 밖에 `#mucom88`, `#driver`, `#version`, `#uuid`, `#mucmd5`도 알려진 태그 이름으로 취급합니다. 그렇다고 해당 태그를 적으면 새 드라이버나 확장 문법으로 컴파일 엔진이 전환된다는 뜻은 아닙니다. `#mucmd5`를 적는 것과 [입력별 `.MD5` 파일](#18)을 준비하는 것도 별개입니다.

태그를 적을 때에는 다음처럼 정리해 주세요.

- `#`를 행 맨 앞에 둡니다.
- 메타데이터 태그는 파일 시작 부분에 연속해서 모읍니다.
- 태그 사이에 일반 주석이나 공백만 있는 행을 끼워 넣지 않습니다.
- 음악 데이터가 시작된 뒤에 `#voice`, `#pcm`, `#title`을 뒤늦게 추가하지 않습니다.
- 헤더를 소스 전반에 흩어 놓거나 수만 바이트 길이로 만들지 않습니다.

현재 메타데이터 처리는 처음 헤더 구간, 첫 소스 메모리 창을 기준으로 합니다. 큰 MUC의 뒤쪽까지 음악 행을 처리할 수 있다는 사실과, 파일 어디에 둔 태그든 적용한다는 것은 다른 이야기입니다.

헤더 밖의 태그는 무시되었다는 경고가 나올 수 있습니다. 인식하지 못한 태그도 경고 대상입니다. 이런 태그가 원문 텍스트로 남는 경우와 실제 컴파일 설정으로 반영되는 경우를 혼동하지 마세요.

## 8. FM 음색 준비하기

FM 음색은 주로 외부 라이브러리에서 가져오거나, MUC 안에 직접 정의합니다.

### 외부 음색 파일

```muc
#voice VOICE.DAT
A @1 o4 c
```

태그를 생략하면 기본 이름은 `VOICE.DAT`입니다. 현재 외부 라이브러리 로더는 8,192바이트, 즉 32바이트 단위 음색 레코드 256개 영역을 사용합니다. 다른 형식의 음색 파일을 이름만 바꿔 넣으면 안 됩니다.

중요한 점이 하나 있습니다. **음색 파일을 열지 못하면 현재 버전은 음색 영역을 0으로 초기화한 뒤 계속 진행할 수 있습니다.** 모든 외부 음색 누락을 친절한 오류로 잡아 주는 것은 아닙니다. 번호로 선택한 음색은 조용히 잘못된 내용이 들어갈 수 있습니다. 짧거나 손상된 음색 파일에 대해서도 완전한 형식 검증을 기대하지 마십시오.

따라서 FM 곡의 소리가 이상하다면 가장 먼저 다음을 확인하세요.

1. 이 곡에 맞는 음색 파일인가?
2. 현재 작업 폴더에 있는가?
3. `#voice`의 이름과 DOS에서 보이는 이름이 맞는가?
4. 라이브러리의 크기와 내용이 원본과 같은가?
5. 소스의 `@번호` 또는 `@"이름"`이 그 라이브러리를 기준으로 작성되었는가?

### 긴 음색·PCM 이름

입력 MUC의 긴 이름은 거부하지만, `#voice`와 `#pcm`의 자산 이름은 기존 FCB 방식의 축약 동작을 유지합니다.

```muc
#voice shinobivoice.dat
```

이 경우 MSX 쪽에는 `SHINOBIV.DAT`라는 이름으로 준비해야 합니다. 일반적인 VFAT의 `SHINOB~1.DAT` 별칭을 자동으로 찾아 주는 기능이 아닙니다.

가능하면 태그와 실제 파일 모두 처음부터 짧고 분명한 8.3 이름으로 맞추세요. 서로 다른 긴 이름이 같은 8.3 이름으로 잘리는 경우에는 폴더를 분리해야 합니다. 단, 원본 MUB와 완전한 바이트 비교를 할 예정이라면 태그 이름을 수정하는 것 자체가 태그와 해시를 바꾼다는 점도 고려해야 합니다.

### 소스 안의 인라인 음색

현재 버전은 여러 행의 `@N` 정의, `@N:{...}` 형식, 원시 파라미터 `@%N` 형식을 처리합니다. 아래는 중괄호 형식의 예입니다.

```muc
  @1:{
7,2
31,8,3,5,2,41,1,1,3
31,5,4,5,2,39,0,5,2
31,4,2,5,1,31,0,3,7
28,30,6,6,0,0,2,1,4
}
A @1 o4 l4 cdef
```

첫 두 값은 FB, ALG이며, 다음 네 행은 각 오퍼레이터의 `AR, DR, SR, RR, SL, TL, KS, ML, DT` 순서입니다. 인라인 정의 앞의 들여쓰기와, 음악 채널 행 앞에 공백을 넣으면 안 된다는 규칙은 서로 다른 경우입니다.

MUC2MUB는 인라인 정의를 음색 영역에 반영한 뒤 실제로 사용한 FM 음색을 결과에 넣습니다. 사용된 음색은 한 개당 25바이트 파라미터로 직렬화됩니다. 외부 라이브러리 전체를 그대로 MUB에 붙이는 것이 아닙니다.

한 곡에서 사용할 수 있는 FM 음색은 최대 32개입니다. 이 제한은 “음색 번호가 32 이하이어야 한다”는 뜻이 아니라, 곡에서 실제로 등록·사용하는 서로 다른 FM 음색 수에 대한 제한입니다.

잘못된 인라인 정의가 모두 명확한 오류로 검출되는 것은 아닙니다. 값의 개수, 순서, 번호를 지키고 실제 재생 또는 원본 DATA 비교까지 해 주세요.

## 9. PCM과 ADPCM

### 어떤 파일을 준비하나

K 채널에서 ADPCM을 사용하는 곡은 그 곡에 맞는 PCM 뱅크 파일이 필요합니다.

```muc
#pcm PCM.BIN
```

태그가 없을 때 기본 파일명은 `MUCOMPCM.BIN`입니다. 확장자가 반드시 `.PCM`이어야 하는 것은 아닙니다. `.BIN` 등 원래 곡이 사용하던 이름을 따르되 DOS 파일명 규칙에 맞춰 준비합니다.

여기서 말하는 PCM 파일은 MUCOM88에서 사용할 수 있도록 준비된 데이터입니다. 일반 WAV나 MP3의 확장자만 바꾸어 넣는 것이 아닙니다. 컴파일러가 오디오 형식을 분석해서 OPNA용 ADPCM으로 변환해 주지는 않습니다.

### 언제 MUB에 들어가나

음악 이벤트와 FM 음색 데이터는 먼저 메모리 매퍼에 만들어 둡니다. PCM 블록 전체는 그곳에 함께 올려 두지 않습니다.

저장 단계에서 PCM 파일 크기를 확인하고, 디스크에서 조금씩 읽어 MUB의 태그 뒤에 이어 씁니다. 정상적인 K 채널 사용 곡에서는 필요한 PCM 뱅크가 포함된 하나의 MUB가 만들어지는 방식입니다.

- PCM은 메모리의 음악 DATA와 별도입니다.
- PCM 파일 자체의 바이트를 이어 붙이며, 저장할 때 다시 음성 압축을 하지는 않습니다.
- 사용한 샘플만 골라 PCM 뱅크를 자동으로 잘라 주지는 않습니다.
- K 채널을 사용하지 않으면 PCM 파일이 있어도 PCM 블록을 포함하지 않습니다.
- PCM 크기는 32비트로 취급하므로 64 KiB보다 큰 PCM도 저장 경로에서 처리합니다. 이것이 임의 크기·형식의 모든 PCM이나 모든 플레이어의 지원을 보장한다는 뜻은 아닙니다.

### PCM 누락 경고

```text
Warning: PCM file not found: PCM.BIN
```

이 경고가 나와도 컴파일을 마치고 MUB를 만들 수 있습니다. 기존 동작과의 호환성을 유지한 부분입니다.

K 채널을 사용하는 곡이라면 정상 완성으로 취급하지 마세요. FM과 SSG는 들리는데 샘플 소리만 빠진 결과일 수 있습니다. 파일을 준비한 후 다시 컴파일해야 합니다.

K 채널이 없는 곡에서도 PCM 크기를 조회하는 과정 때문에 누락 경고가 나올 수 있습니다. 그 경우에는 곡이 원래 PCM을 사용하지 않는다는 것을 확인하면 됩니다.

파일을 찾지 못하는 것과, 찾은 파일을 실제로 읽다가 실패하는 것은 다릅니다. 후자는 `Cannot read PCM file` 오류가 되어 저장에 실패할 수 있습니다. 컴파일 중에는 PCM 파일을 교체하거나 매체를 빼지 마십시오.

## 10. 컴파일과 저장은 어떻게 진행되는가

전체 흐름은 다음과 같습니다.

```text
MUC 읽기
  ↓
행 경계를 유지하여 소스를 매퍼에 적재
  ↓
음색 준비 → 채널별 일괄 컴파일 → 음악·FM DATA 완성
  ↓
임시 파일에 헤더 + DATA + 태그 기록
  ↓
필요한 PCM을 디스크에서 읽어 이어 붙임
  ↓
파일 닫기 → 최종 MUB 이름으로 교체
```

소스를 읽으면서 바로 최종 MUB에 음표를 써 내려가는 방식이 아닙니다. 먼저 소스를 적재하고, 채널별로 컴파일한 음악 DATA를 메모리에 구성한 뒤 디스크에 저장합니다. 내부 저장 방식은 행 경계를 유지한 매퍼 창과 작업용 행 버퍼이며, 64 KiB를 Z80의 한 연속 주소 공간에 모두 펼쳐 놓아야 하는 구조는 아닙니다.

출력 파일의 큰 구성은 다음과 같습니다.

| 순서 | 내용 |
|---|---|
| 1 | 80바이트 MUB8 헤더 |
| 2 | 음악 DATA: 채널 테이블, 이벤트, 사용 FM 음색 등 |
| 3 | 태그: 곡 정보와 추가 메타데이터 |
| 4 | 필요한 경우 PCM 뱅크 |

메모리에서 완성된 음악 DATA는 저장 단계에서 다시 MML로 해석하거나 재컴파일하지 않고 기록합니다. 다만 최종 MUB에는 헤더·태그·PCM도 필요하므로 “매퍼 메모리 전체를 그대로 덤프한 파일”은 아닙니다.

컴파일 과정의 문법·길이·버퍼 검사와 저장 시 I/O 검사는 수행하지만, 만들어진 곡을 자동으로 재생해 원곡과 청각적으로 비교하거나 저장 파일 전체를 다시 읽어 원본 MUB와 대조하는 기능은 없습니다. 완전 일치 검증은 별도의 비교 절차입니다.

<a id="11"></a>

## 11. 메모리와 크기 제한

이 부분은 서로 다른 크기를 구분해서 보아야 합니다.

| 대상 | 현재 기준 |
|---|---|
| 입력 MUC | 디스크상의 실제 크기 최대 65,536바이트, 즉 64 KiB |
| 소스 적재용 매퍼 | 행 경계를 유지하기 위해 16 KiB 세그먼트 5개 사용 |
| 음악·FM 출력 DATA | 16 KiB 세그먼트 2개, 32 KiB 영역 안에 들어가야 함 |
| 음색·작업용 매퍼 | 16 KiB 세그먼트 1개 |
| 작업 매퍼 할당 합계 | 8세그먼트 = 128 KiB. DOS·프로그램·그 밖의 메모리는 별도 |
| 일반 채널 행의 MML 본문 | `A ` 같은 앞의 두 바이트 뒤로 최대 1,023바이트 |
| 매크로 본문 | 최대 511바이트 |
| 반복 중첩 | 최대 16단계 |
| 매크로 호출 중첩 | 최대 4단계 |
| 한 곡에서 사용한 FM 음색 | 최대 32개 |

### 64 KiB에는 무엇이 포함되나

음표뿐 아니라 제목 태그, 주석, 공백, 개행까지 포함한 파일 전체 바이트입니다. 64,000바이트와 65,536바이트를 혼동하지 마세요. 65,536바이트는 허용 범위지만 65,537바이트는 초과입니다.

16·32·48·64 KiB 규모의 소스를 처리할 수 있습니다. 하지만 크기가 한도 이하라는 사실만으로 모든 소스가 성공하는 것은 아닙니다. 문법, 한 행 길이, 매크로 길이, 최종 DATA 크기 등의 조건도 만족해야 합니다.

특히 주석 한 행을 수만 자로 늘이거나, 개행 없이 전체 곡을 한 행에 몰아 넣는 방식은 피하세요. 아주 긴 비음악 행도 소스 메모리 창의 적재 한계를 만날 수 있습니다. 읽기 좋은 여러 행으로 나누는 것이 좋습니다.

### 입력 크기와 출력 크기는 비례하지 않는다

주석이 많은 64 KiB MUC의 음악 DATA가 작은 경우도 있고, 음표·매크로 호출이 빽빽한 더 작은 MUC가 출력 영역을 먼저 채울 수도 있습니다. 출력 DATA에는 음표뿐 아니라 채널 구조와 음색 테이블도 들어갑니다. 32 KiB를 음표만으로 전부 사용할 수 있다고 계산하지 마세요.

출력 공간이 부족하면 음악적으로 같은 결과를 유지할 수 있는 반복 구문으로 정리하거나 곡을 나누어야 합니다. 주석만 줄이는 것은 입력 크기에는 도움이 되지만 이미 커진 음악 DATA를 줄이지는 못합니다.

최종 `.MUB` 파일은 헤더·태그·PCM까지 포함하므로 32 KiB나 64 KiB보다 커질 수 있습니다. 파일이 크다는 이유만으로 DATA 한도를 넘었다고 판단해서는 안 됩니다.

### 4 MiB RAM을 꽂으면 제한이 늘어나나

아닙니다. 4 MiB 매퍼 검증은 그 구성에서 정상 동작하는지 확인한 것이지, 전체 4 MiB를 예약하거나 사용하는 시험이 아닙니다.

현재 컴파일러는 DOS의 기본 매퍼 컨텍스트에서 필요한 8개의 사용자 세그먼트를 할당합니다. 모든 슬롯의 RAM을 직접 조사하여 용량을 합산하거나 다른 매퍼의 여유 공간을 적극적으로 모으는 방식은 아닙니다. 물리 RAM 총량이 커도 DOS가 제공하는 할당 여건에 따라 메모리 오류가 날 수 있습니다.

RAM 증설만으로 입력 64 KiB, 음악 DATA 32 KiB 영역, 행·매크로 길이 제한이 자동으로 늘어나지는 않습니다.

<a id="12"></a>

## 12. 여러 곡을 배치 변환하기

MUC2MUB는 한 번에 한 곡을 처리합니다. 여러 곡을 순서대로 부르는 일은 DOS 셸이나 배치 파일이 맡습니다.

### 가장 간단한 배치 파일

아래 내용을 `BUILD.BAT`로 준비합니다. 이 절의 명령은 MSX-DOS에서 실행하는 예입니다.

```bat
@ECHO OFF
MUC2MUB SONG01.MUC
MUC2MUB SONG02.MUC
MUC2MUB SONG03.MUC
```

```dos
BUILD
```

이 예제는 순서대로 실행하는 기본형입니다. **중간 곡이 실패했을 때 자동으로 중단하거나 실패 목록을 모아 주는 배치가 아닙니다.** 마지막 명령의 성공만 보고 전부 성공했다고 판단하지 마세요.

곡별 기록을 남기려면 출력을 따로 보관할 수 있습니다.

```bat
@ECHO OFF
MUC2MUB SONG01.MUC > C01.LOG
MUC2MUB SONG02.MUC > C02.LOG
MUC2MUB SONG03.MUC > C03.LOG
```

리다이렉션하면 화면에 진행 표시가 보이지 않을 수 있습니다. 로그 이름은 소스·음색·PCM·기존 MUB와 겹치지 않게 정하세요. 같은 로그에 `>`로 다시 기록하면 앞선 로그가 교체됩니다. 로그 작성에도 디스크 공간이 필요합니다.

### 앨범이 여러 폴더에 있는 경우

다음 예제는 각 앨범 폴더에서 `MUC2MUB` 명령을 찾을 수 있다는 전제입니다.

```bat
@ECHO OFF
CD \ALBUM1
MUC2MUB SONG01.MUC
MUC2MUB SONG02.MUC
CD \ALBUM2
MUC2MUB SONG01.MUC
MUC2MUB SONG02.MUC
```

각 폴더에는 그 앨범의 음색·PCM 파일을 둡니다. 드라이브도 다르다면 `CD`만 하지 말고 해당 드라이브로 전환하세요.

와일드카드 반복이나 조건부 중단을 추가하려면 사용하는 MSX-DOS 셸의 문법을 확인해야 합니다. Windows의 `FOR` 예제를 그대로 복사해 동작한다고 가정하지 마세요. MUC2MUB 자체에는 파일 목록 반복이나 “실패한 곡만 재시도” 기능이 없습니다.

### 배치 운영 원칙

- 처음에는 한 곡, 다음에는 작은 묶음, 마지막에 전체 앨범 순서로 진행합니다.
- 실행 전에 대상 목록과 각 곡의 자산을 확인합니다.
- 실패해도 계속할지, 첫 실패에서 멈출지는 셸 쪽에서 명시적으로 정합니다.
- 종료 코드와 함께 로그의 경고도 확인합니다.
- 실패한 자리에 남아 있는 기존 MUB를 새 결과로 잘못 집계하지 않습니다.
- 동일 출력 폴더에서 여러 변환을 동시에 실행하지 않습니다. 임시 파일 이름이 고정되어 있습니다.
- `M2MTEMP.$$$`와 `M2MBACK.$$$`를 배치 시작 때 무조건 삭제하지 않습니다.
- 중단 후에는 결과 목록을 다시 확인하고, 필요한 곡부터 재실행합니다.

특히 보관용 일괄 변환에서는 “프로그램이 전부 실행됐다”와 “모든 곡이 올바르게 변환됐다”를 구분하는 것이 중요합니다.

## 13. 성공·경고·오류와 종료 코드

| 상태 | 의미 | DOS 종료 코드 |
|---|---|---|
| 정상 완료 | 컴파일과 저장 절차 완료 | `0` |
| 경고 후 완료 | 무시된 행·태그 또는 누락 자산 등이 있을 수 있음 | 완료되었다면 `0`일 수 있음 |
| 일반 오류 | 인수, 컴파일, 파일 I/O, 메모리 등 실패 | `1` |
| DOS에 의한 중단 | Ctrl-C, STOP, 매체 오류 등으로 DOS 중단 처리 | DOS의 해당 중단·오류 코드 |

화면의 컴파일 오류 번호와 DOS 종료 코드는 서로 다릅니다.

```text
Error line 4, channel A (code 6): Note length out of range
> A l0 c
```

이 예제의 `code 6`은 음길이 오류의 분류 번호입니다. DOS 셸에 6을 반환한다는 뜻이 아닙니다. 일반적인 컴파일 실패의 종료 코드는 1입니다.

오류 위치는 MUC의 실제 행 번호와 채널로 표시합니다. 행 내용은 앞부분 최대 72바이트까지만 보여 주므로 긴 행의 뒷부분은 원본 편집기에서 확인해야 합니다. 매크로 안의 오류는 호출한 음악 행을 기준으로 표시될 수 있으므로 매크로 정의도 같이 보세요.

소스 위치를 특정하지 못하면 `Error (source line unavailable)`로 시작하는 메시지가 나옵니다. 오류가 없다는 뜻이 아니라 위치 정보를 붙이지 못했다는 뜻입니다.

일반적으로 첫 오류부터 고치고 다시 컴파일하세요. 한 번에 전체 소스의 모든 오류를 모아 출력하는 방식은 아닙니다.

<a id="14"></a>

## 14. 컴파일 오류 전체 안내

아래는 현재 진단 메시지의 전체 분류입니다. 예제는 대표적인 발생 조건이지 가능한 모든 잘못된 문법을 나열한 것은 아닙니다.

| 코드 | 화면 메시지 | 원인과 확인할 부분 |
|---|---|---|
| 0 | `Syntax error / missing number` | 해석할 수 없는 문법 또는 필요한 숫자 누락. 직전 명령의 매개변수를 확인 |
| 1 | `Invalid parameter` | 해당 명령에 부적절한 값. 지나치게 큰 수, 부호, 값 범위를 확인 |
| 2 | `Repeat end without matching start` | 대응하는 `[` 없이 `]` 사용 |
| 3 | `Unclosed repeat/loop` | `[`로 연 반복이 채널 종료까지 닫히지 않음 |
| 4 | `Too many voices (maximum 32)` | 사용 FM 음색이 32개를 초과. 실제 사용 음색을 정리 |
| 5 | `Octave out of range (o1..o8)` | 옥타브가 지원 범위를 벗어남. `o`와 `<`, `>` 흐름 확인 |
| 6 | `Note length out of range` | 유효하지 않은 음길이. 특히 `l0`, 0 또는 계산 불가능한 길이 확인 |
| 7 | `Invalid loop escape` | 반복 밖의 `/` 또는 같은 반복에 중복된 탈출 표시 |
| 8 | `Missing parameter or separator` | 필요한 매개변수·구분자 누락. 여러 숫자를 받는 명령의 쉼표와 값 확인 |
| 9 | `Command not valid for this channel` | 현재 채널에서 사용할 수 없는 명령. FM·SSG·리듬·ADPCM 구분 확인 |
| 10 | `Too many nested repeats` | 반복 중첩 16단계 초과. 반복 구조를 단순하게 정리 |
| 11 | `Voice name not found or invalid` | 이름으로 지정한 음색을 찾지 못했거나 이름 지정이 부적절함. 음색 라이브러리와 철자 확인 |
| 12~14 | `Unspecified compiler error` | 예약되었거나 일반 사용자용 의미가 정의되지 않은 분류. 숫자를 보존하여 제보 |
| 15 | `Macro not found` | 호출한 번호의 매크로 정의가 없음 |
| 16 | `Invalid macro definition` | 매크로 정의 형식·중괄호 문제 또는 재귀·호출 중첩 한계 |
| 17 | `MML line or macro too long` | 음악 행 또는 매크로 본문이 작업 버퍼 한도를 초과 |
| 18 | `Output buffer overflow` | 음악 이벤트와 음색 등을 담는 출력 영역 부족 |

정의되지 않은 다른 번호도 `Unspecified compiler error`로 표시될 수 있습니다. 코드 번호만 보고 임의로 새로운 의미를 붙이지 말고, 원문과 발생 조건을 함께 보관해 주세요.

### 흔히 만나는 오류 예제

다음은 일부러 잘못 작성한 예입니다. 정상 곡 예제로 사용하지 마세요.

```muc-error
A l0 c
```

기본 음길이가 0입니다. 의도한 길이가 4분음표라면 `l4`처럼 고칩니다.

```muc-error
A ]2
```

닫는 반복만 있습니다. 시작 `[`가 필요합니다.

```muc-error
A [c
```

반복이 닫히지 않았습니다. 의도에 맞는 `]횟수`로 마무리합니다.

```muc-error
A /c
A [c / d / e]2
```

첫 행은 반복 밖에서 `/`를 사용했고, 둘째 행은 같은 반복에 `/`를 두 번 사용했습니다.

```muc-error
A q100000 c
```

명령이 받아들일 수 없는 큰 값입니다. 숫자를 무작정 줄이는 것보다는 해당 명령의 의미와 원하는 효과부터 확인하세요.

```muc-error
A *99
```

99번 매크로를 정의하지 않았다면 오류입니다. `# *99{...}` 정의가 존재하는지 확인합니다.

```muc-error
# *1{*1}
A *1
```

매크로가 자기 자신을 계속 부릅니다. 반복이 필요하다면 재귀가 아니라 반복 구문으로 표현해야 합니다.

### 긴 행을 나누는 방법

```muc
A o4 l8 cdefgab>c
A <bagfedcr
```

앞 행과 같은 채널 문자를 다음 행에도 적습니다. 화면상의 자동 줄바꿈만으로는 실제 파일의 한 행이 나뉘지 않습니다. 편집기에서 개행 문자를 넣어야 합니다.

매크로 길이 초과라면 본문을 짧게 나누고 호출 구조도 단순하게 정리합니다. 행을 나누는 것만으로 매크로 본문 전체 크기 제한이 사라지는 것은 아닙니다.

## 15. 경고 메시지 안내

경고는 소스를 자동으로 고쳤다는 뜻이 아닙니다. 일부 내용을 무시한 채 결과를 만들 수 있으므로, 의도한 곡이 맞는지 확인해야 합니다.

| 메시지 | 의미 | 해결 방법 |
|---|---|---|
| `Invalid channel prefix; use A-K + space/tab` | 올바르지 않은 채널 행 | 행 첫 칸의 대문자 A~K, 다음 공백·탭 확인. 들여쓰기·쉼표·소문자 수정 |
| `Unknown or malformed tag` | 알려지지 않은 태그 또는 잘못된 태그 표기 | 태그 이름·형식을 확인. 다른 컴파일러 전용 태그인지 검토 |
| `Missing tag value` | 값을 요구하는 태그에 값이 없음 | 제목·파일명 등 필요한 값을 채움. 빈 `#comment`는 허용 |
| `Tag outside initial header is ignored` | 처음 헤더 구간 밖의 태그 | 파일 맨 위의 연속된 헤더로 이동 |
| `Warning: PCM file not found:` | 지정 또는 기본 PCM 파일을 찾지 못함 | K 채널 사용 여부, 현재 폴더, 실제 8.3 이름 확인 |

행 관련 경고는 다음처럼 나옵니다.

```text
Warning line 4: Invalid channel prefix; use A-K + space/tab
>  A o4 c
```

“경고가 있었지만 정상 종료했다”는 결과를 배치 집계에서 그냥 성공으로 합치지 마세요. 적어도 경고가 의도된 것인지 확인한 뒤 최종 성공으로 분류하는 것이 좋습니다.

반대로 경고가 하나도 없다는 사실만으로 외부 음색 파일의 내용이나 PCM 형식이 맞다고 판단해서도 안 됩니다. 현재 모든 자산 문제가 경고 대상으로 잡히는 것은 아닙니다.

## 16. 파일·디스크·메모리 오류

이 오류들은 MML 문법을 고치는 것만으로 해결되지 않을 수 있습니다.

| 화면 메시지 | 먼저 확인할 사항 |
|---|---|
| `Usage: MUC2MUB <input.muc> [output.mub]` | 입력 인수가 있는지, 기본 호출 형식을 지켰는지 |
| `Invalid name/arguments (input: 8.3, no path).` | 긴 입력 이름, 경로, 따옴표, 공백, 추가 인수, 인수 길이, 출력 파일명·입력 보호 검사 |
| `Cannot open input file` | 현재 드라이브·폴더, 실제 DOS 파일명, 파일 존재 여부 |
| `Cannot read input file` | 매체 읽기 문제, 손상 파일, 연결 상태 |
| `Input exceeds 64 KiB.` | 원시 파일 65,536바이트 초과 여부. 아주 긴 행에 따른 적재 한계도 점검 |
| `Error: Mapper unavailable or insufficient memory.` | DOS 2 매퍼 서비스, 할당 가능한 세그먼트, 메모리를 점유한 다른 프로그램 |
| `Cannot create output file` | 출력 폴더 존재, 쓰기 가능 여부, 이름·경로 길이, 읽기 전용 대상, 남은 임시·백업 파일, 디렉터리 항목 여유 |
| `Cannot write output file` | 디스크 공간, 쓰기 금지, 매체 오류. 요청보다 적게 써진 경우도 실패 처리 |
| `Cannot close output file` | 파일 닫기뿐 아니라 최종 이름 교체·백업 정리 실패 가능성. 최종·임시·백업 파일 모두 확인 |
| `Cannot read PCM file` | PCM 읽기 도중 실패 또는 저장 단계에서 PCM을 다시 열지 못함 |
| `Output buffer overflow` / `Error: output buffer overflow` | 음악 DATA가 출력 영역에 들어가지 않음. 입력 크기·디스크 공간과 별개의 문제 |

### 디스크는 비어 있는데 생성에 실패한다면

여유 바이트만 보지 말고 다음도 확인해 주세요.

- 목적 폴더가 실제로 있는가?
- 기존 출력이 읽기 전용이나 시스템 파일인가?
- 같은 이름의 디렉터리 등이 있는가?
- `M2MTEMP.$$$` 또는 `M2MBACK.$$$`가 이미 있는가?
- 특히 FAT 루트 디렉터리의 파일 항목이 가득 차지 않았는가?
- 출력 경로가 너무 길지 않은가?

프로그램은 읽기 전용 속성을 임의로 해제하지 않습니다. 기존 파일이 왜 보호되어 있는지 먼저 확인하세요.

### RAM이 충분해 보이는데 시작하지 못한다면

DOS에서 매퍼를 제공하고 있는지, 기본 할당 대상에서 8세그먼트를 확보할 수 있는지 확인합니다. 다른 프로그램이 메모리를 사용한 상태라면 종료한 뒤 다시 시도하세요. 물리 RAM 총량과 DOS가 지금 할당할 수 있는 메모리는 같은 값이 아닙니다.

### 오류 뒤에 MUB가 남아 있다면

그 파일은 방금 만든 결과가 아니라 이전에 정상적으로 저장되어 있던 파일일 수 있습니다. 원본 보호를 위해 남겨 둔 것입니다. 파일이 있다는 이유만으로 이번 변환을 성공으로 판단하지 마세요.

<a id="17"></a>

## 17. 안전 저장과 중단 후 복구

이미 있는 MUB를 처음부터 잘라서 다시 쓰는 방식은 사용하지 않습니다. 새 결과를 임시 파일로 완성한 뒤 교체합니다.

### 정상 저장 순서

1. 출력 폴더에 `M2MTEMP.$$$`를 새로 만듭니다.
2. 새 MUB의 내용을 끝까지 기록하고 닫습니다.
3. 기존 출력이 있으면 이름을 `M2MBACK.$$$`로 바꿉니다.
4. 임시 파일을 요청한 최종 MUB 이름으로 바꿉니다.
5. 정상 교체 후 이전 파일의 백업을 정리합니다.

저장 중에는 이전 결과와 새 결과가 함께 존재할 공간이 필요합니다. 기존 MUB를 남긴 채 새 MUB 전체를 쓸 여유를 확보하세요. 백업은 이전 파일의 이름을 바꾸는 것이므로 이전 데이터의 세 번째 전체 복사본을 만드는 방식은 아닙니다. 다만 디렉터리 항목은 추가로 필요합니다.

임시 파일 쓰기·닫기가 실패하면 기존 최종 파일을 보존합니다. 이름 교체가 실패하면 이전 이름으로 복구를 시도합니다. 복구마저 실패했을 때는 이전 파일의 바이트를 `M2MBACK.$$$`에 남깁니다.

교체가 끝난 뒤 백업 삭제만 실패하는 경우도 있습니다. 이 경우 오류가 표시되더라도 새 최종 MUB와 이전 백업이 함께 있을 수 있습니다. 메시지만으로 어느 파일이 최신인지 단정하지 말고 내용을 확인하세요.

### 임시 파일 이름은 예약해 두세요

`M2MTEMP.$$$`와 `M2MBACK.$$$`가 이미 있으면 프로그램은 함부로 덮어쓰지 않고 중단합니다. 사용자가 만든 파일이나 이전 실패의 복구 자료일 수 있기 때문입니다. 출력 이름으로 이 두 이름을 사용하지 마십시오.

### Ctrl-C, STOP, 매체 오류

DOS 중단 처리에서는 자신이 열어 둔 임시 출력 핸들을 정리하려고 시도합니다. 그러나 디스크 자체가 쓰기 불능이면 임시 파일 삭제까지 성공한다고 보장할 수 없습니다.

Ctrl-C나 STOP은 현재 곡뿐 아니라 BAT 전체의 중단으로 이어질 수 있습니다. DOS가 배치 종료 여부를 물으면 화면의 질문에 따라 응답하세요. 중단 후 같은 BAT가 저절로 이어서 실행된다고 가정하지 마십시오.

### 다시 실행하기 전 복구 순서

1. 매체를 안정적으로 연결하고, 현재 폴더와 출력 폴더를 확인합니다.
2. 최종 MUB, `M2MBACK.$$$`, `M2MTEMP.$$$`의 존재와 크기를 확인합니다.
3. 남은 백업·임시 파일은 먼저 다른 이름이나 다른 매체로 보관합니다.
4. 백업이 이전 정상 파일인지 확인합니다. 임시 파일은 불완전할 수 있으므로 그대로 배포하지 않습니다.
5. 최종 파일이 없고 백업이 이전 정상 결과라면, 그 백업을 보존한 뒤 복구합니다.
6. 공간·속성·매체 문제를 해결하고, 예약 파일명이 충돌하지 않도록 정리한 다음 다시 컴파일합니다.

예를 들어 백업 내용이 이전 정상 MUB임을 확인했다면 `RECOVER.MUB` 같은 이름으로 복사하여 보관할 수 있습니다. 여기서는 내용을 확인하지 않고 일괄 삭제하는 복구 명령을 안내하지 않습니다. 복구 가능성을 먼저 남기는 것이 중요합니다.

이 저장 방식도 전원 차단이나 FAT 손상까지 원자적으로 보장하는 것은 아닙니다. 중요한 원본과 완성본은 별도 매체에도 백업해 주세요.

## 18. 원본 MUB와 비교하기, MD5 사용법

### 무엇이 같아야 “같은 MUB”인가

비교 수준을 나누어 보면 원인을 찾기 쉽습니다.

| 비교 대상 | 확인하는 내용 |
|---|---|
| 음악 DATA | 채널 이벤트와 실제 FM 음색 파라미터가 같은가 |
| PCM 블록 | 같은 뱅크의 같은 바이트가 포함되었는가 |
| 태그·헤더 | 제목, 개행, 길이·오프셋, 추가 메타데이터가 같은가 |
| 전체 파일 | 처음부터 끝까지 모든 바이트와 전체 길이가 같은가 |

FM 음색 개수나 채널 테이블이 같아도 실제 25바이트 음색 파라미터가 다를 수 있습니다. DATA 크기가 같다는 것 역시 DATA 내용이 같다는 뜻은 아닙니다.

### 입력별 `.MD5` 파일

현재 버전은 MUC 원문 해시를 넣기 위해 입력과 같은 이름의 `.MD5` 파일을 읽습니다.

```text
SONG.MUC  →  SONG.MD5
BOS010.MUC  →  BOS010.MD5
```

출력 파일을 `TEST.MUB`로 지정해도 입력이 `SONG.MUC`라면 해시 파일은 `SONG.MD5`입니다. 예전의 공통 `MUBHASH.TXT`는 사용하지 않습니다.

파일 내용의 조건은 다음과 같습니다.

- 해당 MUC **원문 바이트 전체**의 MD5입니다.
- ASCII 16진수 32자만 넣습니다.
- 줄바꿈, BOM, 공백, 파일명은 넣지 않습니다.
- 파일 크기는 정확히 32바이트여야 합니다.
- 대문자 16진수도 받지만 출력에는 소문자로 정규화합니다.

`.MD5`가 없거나 크기·문자가 잘못되었거나 읽기에 실패하면 `#mmlhash`에 ASCII 문자 `0`을 32개 기록합니다. 이는 MUB 전체나 음악 DATA를 0으로 만든다는 뜻이 아닙니다.

무엇보다 **MSX에서 MD5를 계산하여 원문과 대조하는 기능이 아닙니다.** 형식이 맞는 외부 값을 받아 넣는 기능입니다. 오래된 `.MD5`가 형식만 맞으면 그대로 들어갈 수 있으므로, MUC를 수정했으면 해시도 다시 만들어야 합니다.

### PC에서 `.MD5` 만들기

아래는 MSX-DOS 명령이 아니라 **PC의 Python 3에서 실행하는 예제**입니다. 작업 폴더의 `SONG.MUC`를 읽고 `SONG.MD5`를 생성하거나 갱신합니다.

```python
from pathlib import Path
import hashlib

source = Path("SONG.MUC")
digest = hashlib.md5(source.read_bytes()).hexdigest()
source.with_suffix(".MD5").write_bytes(digest.encode("ascii"))
```

바이너리로 읽고 쓰기 때문에 줄바꿈을 변환하지 않으며, `.MD5` 끝에 개행도 붙이지 않습니다. 만들어진 파일을 MUC와 함께 MSX 쪽으로 옮기세요. 전송 과정에서 MUC의 문자 인코딩이나 개행을 바꾸면 다시 계산해야 합니다.

### 원본과 완전히 일치시키려면

1. MUC가 같은 원문 바이트인지 확인합니다.
2. 동일한 FM 음색 라이브러리와 PCM 뱅크를 사용합니다.
3. 입력에 맞는 `.MD5`를 준비합니다.
4. 같은 문법·호환 기준의 컴파일 결과끼리 비교합니다.
5. 헤더, DATA, 태그, PCM을 구분하여 차이를 찾습니다.

원본 MUB가 다른 버전·옵션·메타데이터 규칙으로 만들어졌다면 음악 DATA가 같아도 전체 파일은 다를 수 있습니다. 이 버전의 추가 태그에는 `#mucver 1.7d`, `#mmlhash`, 고정 UUID가 들어갑니다. 이 UUID를 곡마다 새로 계산한 고유 식별자라고 해석하지 마세요.

간단한 전체 바이트 비교도 PC에서 할 수 있습니다.

```python
from pathlib import Path

original = Path("ORIGINAL.MUB").read_bytes()
compiled = Path("TEST.MUB").read_bytes()
print("완전 일치" if original == compiled else "차이 있음")
print("원본:", len(original), "바이트 / 결과:", len(compiled), "바이트")
```

이 비교는 길이까지 포함한 완전 일치 검사입니다. 차이가 있다고 나왔다고 해서 곧바로 컴파일러의 음악 DATA 오류라고 단정하지 말고, 어느 섹션이 다른지 확인하세요. 반대로 잘 들린다는 이유로 바이너리 차이를 없는 것으로 취급해서도 안 됩니다.

## 19. mucplay·mucEdit·mubplay와 함께 쓰기

각 프로그램의 역할은 다음처럼 나누어 생각하면 편합니다.

- **muc2mub**: DOS에서 MUC를 컴파일하여 MUB 파일로 저장합니다.
- **mucplay**: MUC를 컴파일하고 재생하는 작업에 사용합니다.
- **mucEdit**: 소스를 편집하고 mucplay와 연계하여 확인하는 작업에 사용합니다.
- **mubplay**: 만들어진 MUB를 재생하는 쪽에 사용합니다.

공유 컴파일러를 사용하는 프로그램은 서로 맞는 최신 빌드 조합을 쓰는 것이 좋습니다. 오래된 실행 파일이 다른 폴더나 DOS 검색 경로에 남아 있으면 새 버전을 시험했다고 생각하면서 이전 버전을 실행할 수 있습니다.

muc2mub가 읽는 것은 **디스크에 저장된 MUC**입니다. 편집기에 미저장 변경이 남아 있다면 별도로 실행한 muc2mub는 그 변경을 알 수 없습니다. 독립 변환을 하기 전에 소스를 저장하세요.

standalone muc2mub의 64 KiB 입력 지원을 mucEdit의 편집 버퍼 한도로 그대로 해석하지 마십시오. 현재 연계 편집기는 별도의 정규화 소스 24 KiB 한도가 있습니다. 큰 파일을 독립 컴파일할 수 있다는 것과 편집기에서 같은 크기를 편집할 수 있다는 것은 다릅니다.

편집기 연계나 mucplay의 지속 세션에서는 미저장 편집 내용을 예전 원문 파일의 MD5로 표시하지 않습니다. 따라서 음악 DATA가 같더라도 단독 muc2mub와 `#mmlhash`가 다를 수 있습니다. 이때 해시 차이와 음악 데이터 차이를 분리해서 비교하세요.

## 20. 자주 묻는 질문

### Z80 모드에서도 되나요?

네. Z80을 대상으로 하는 DOS 프로그램이며 Z80 구성에서 검증했습니다. R800이 필수는 아닙니다.

### 평균 컴파일 시간은 어느 정도인가요?

소스 크기만으로 정해지지 않습니다. 채널 구성, 이벤트 수, 매크로, 음색, PCM 크기, 저장 장치와 DOS 환경에 따라 달라집니다. 에뮬레이터의 가속 실행 시간도 실기 Z80의 시간과 같지 않습니다. 이 설명서에서는 근거 없는 평균 초 수를 제시하지 않습니다.

측정할 때는 CPU 모드, 에뮬레이터 속도 설정, 매퍼 구성, 저장 매체, MUC·PCM 크기를 같이 적고 동일 곡을 여러 번 실행해 보세요. 프로그램 시작부터 `Done.`까지의 시간은 순수 컴파일뿐 아니라 파일 읽기와 저장도 포함합니다.

### MUB의 평균 크기는요?

고정된 비율은 없습니다. 주석은 음악 이벤트로 변환되지 않고, 매크로 호출은 이벤트를 늘릴 수 있으며, PCM은 최종 파일 크기를 크게 늘립니다. 먼저 DATA와 PCM 크기를 나누어 보세요.

### 64 KiB MUC면 MUB도 64 KiB까지인가요?

아닙니다. 입력 소스 한도, 음악 DATA 영역, 최종 파일 크기는 각각 다릅니다. 최종 MUB는 PCM 때문에 64 KiB보다 커질 수 있습니다.

### `Done.`인데 FM 소리가 이상합니다.

외부 음색 파일의 존재와 내용, 현재 폴더, 8.3 이름을 먼저 확인하세요. 인라인 정의의 번호·파라미터 순서도 확인합니다. 음색 파일 누락이 항상 오류로 보고되지는 않습니다.

### FM은 나오는데 PCM만 안 나옵니다.

PCM 누락 경고, K 채널 사용 여부, `#pcm` 위치와 파일명, 뱅크 내용, 플레이어의 ADPCM 지원을 차례로 확인합니다. 원래 샘플 파일과 다른 파일을 넣었을 가능성도 살펴보세요.

### 곡 일부 채널만 빠집니다.

채널 행이 들여쓰기되어 있거나 소문자·쉼표 형식인지 확인합니다. 경고 로그와 원본 행을 보세요. 파일 중간의 제어문자, 잘못된 매크로, 지원하지 않는 문법도 확인 대상입니다.

### 없는 PCM 경고를 숨기는 옵션이 있나요?

현재 별도 경고 억제나 엄격 모드 옵션은 없습니다. 로그를 확인하여 PCM이 필요 없는 곡의 경고인지, 실제 누락인지 구분해 주세요.

### 기존 MUB를 덮어쓰지 않게 할 수 있나요?

별도의 무조건 덮어쓰기 금지 옵션은 없습니다. 다른 출력 이름이나 폴더를 지정하십시오. 정상적인 기존 출력은 안전 저장 절차를 거쳐 교체됩니다.

### 실패했는데 예전 MUB가 그대로 있습니다.

기존 결과를 보호한 것입니다. 이번 실행이 성공했다는 뜻은 아닙니다. 로그와 종료 상태를 확인해 주세요.

### 4 MiB RAM인데 출력 버퍼 초과가 납니다.

설치 RAM과 음악 DATA 한도는 다릅니다. 현재 두 출력 세그먼트의 한도는 증설에 따라 자동으로 늘어나지 않습니다.

### `.MD5`가 없으면 컴파일할 수 없나요?

컴파일할 수 있습니다. 원문 해시를 나타내는 부분에 문자 `0` 32개를 넣습니다. 재생용으로 쓰는 것과 원본 MUB 전체 바이트 일치를 확인하는 것은 다른 요구입니다.

### 컴파일만 끝나면 완성본으로 배포해도 되나요?

먼저 경고, 외부 자산, 결과 재생을 확인해 주세요. 원본 재현이 목적이면 바이너리 비교까지 해야 합니다. 컴파일 성공은 완성 확인의 한 단계입니다.

## 21. 배포 전 확인표와 문제 제보

### 한 곡을 완성했을 때

- [ ] 의도한 최신 `MUC2MUB.COM`을 실행했다.
- [ ] 편집한 MUC를 디스크에 저장했다.
- [ ] 곡에 맞는 폴더와 드라이브에서 실행했다.
- [ ] FM 음색·PCM 파일이 올바른 버전과 내용이다.
- [ ] 종료 상태와 경고를 확인했다.
- [ ] 생성된 파일이 예전 MUB가 아니라 이번 결과인지 확인했다.
- [ ] 처음뿐 아니라 곡의 끝, 반복, PCM 사용 구간도 재생해 보았다.
- [ ] 원본 재현 목적이라면 DATA·PCM·태그·전체 바이트를 비교했다.
- [ ] 최종 배포에 필요한 저작권과 자산 사용 조건을 확인했다.
- [ ] 원본 소스와 필요한 자산을 별도로 백업했다.

### 여러 곡을 변환했을 때

- [ ] 예정한 입력 목록과 실제 결과 목록의 수·이름이 맞는다.
- [ ] 각 곡의 실패와 경고를 따로 확인했다.
- [ ] 서로 다른 앨범의 동명 자산을 섞지 않았다.
- [ ] 오류 후 남은 이전 MUB를 새 성공 결과로 세지 않았다.
- [ ] 남은 임시·백업 파일의 내용을 확인하고 필요한 것을 보관했다.
- [ ] 수정한 MUC의 `.MD5`를 다시 만들었다.

### 문제를 알려 주실 때

“컴파일이 안 됩니다”보다 아래 정보를 함께 주시면 원인을 훨씬 빨리 좁힐 수 있습니다.

```text
MUC2MUB 버전:
MSX 기종 / 에뮬레이터와 기종 설정:
CPU 모드:
DOS / Nextor 버전:
메모리 매퍼 구성:
저장 매체:
현재 드라이브와 폴더:
입력한 명령 전체:
MUC 파일명 / 실제 바이트 수 / 인코딩 / 개행:
사용한 음색 파일과 PCM 파일:
경고 및 오류 메시지 전체:
문제가 생기는 최소 소스 또는 해당 행:
기대 결과와 실제 결과:
비교한 원본 MUB의 출처·컴파일 조건:
남은 최종·임시·백업 파일 상태:
```

가능하면 텍스트 로그와 재현 가능한 작은 소스를 함께 보관해 주세요. 음악이나 자산을 공개할 권한이 없다면 먼저 민감한 내용이 없는 최소 재현 예제로 줄이는 것이 좋습니다.

마지막으로 한 가지만 기억해 주세요. **소스와 자산을 맞게 준비하고, 경고를 읽고, 만들어진 곡을 확인하는 것**이 가장 확실한 사용법입니다. 처음에는 조금 번거롭게 느껴져도, 이 순서를 지켜 두면 한 곡을 수정할 때나 수십 곡을 배치 변환할 때나 결과를 믿고 관리하기가 훨씬 편해집니다.
